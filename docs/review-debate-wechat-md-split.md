## Round 1 - Pilot

### 现状

`internal/server/wechat.go` 的 `splitMessage(text, 4000)` 已经有相对完善的切分逻辑：

1. `findSafeCutPoint`（line 763）：优先段落边界 → 表格外 → 换行 → 句末标点 → UTF-8 边界
2. 代码块修复（line 737-750）：未闭合的 ``` 补闭合 + 下段补重开
3. `avoidTableCut`（line 838）：表格行不被截断
4. 测试覆盖：`split_test.go` 有 8 个测试 case（段落、表格、代码块、UTF-8 边界）

**但用户反馈"有时候还是影响 md 渲染"**。

### 我的怀疑（按可能性排序）

**怀疑 1（最可能）：`[i/n]` 前缀破坏行首 Markdown 结构**

`wechat.go:752-755`：
```go
if len(chunks) > 1 {
    for i := range chunks {
        chunks[i] = fmt.Sprintf("[%d/%d] %s", i+1, len(chunks), chunks[i])
    }
}
```

每个 chunk 被加上 `[1/3] `、`[2/3] ` 前缀。如果 chunk 以 md 行首标记开头，前缀会让这些标记**完全失效**：

| chunk 实际开头 | 加前缀后 | 微信渲染结果 |
|--------------|---------|------------|
| `# 标题` | `[1/3] # 标题` | ❌ 不识别为标题 |
| `- 列表项` | `[1/3] - 列表项` | ❌ 不识别为列表 |
| `| 列 \| 列 |` | `[1/3] | 列 \| 列 |` | ❌ 不识别为表格 |
| `> 引用` | `[1/3] > 引用` | ❌ 不识别为引用 |
| ` ```python ` | `[1/3] ```python` | ❌ 不识别为代码块 |

这是**最可能的主因**。测试用例（`TestSplitMessage_TableIntegrity` 等）在验证时手动 strip 掉了 `[i/n] ` 前缀（`split_test.go:25-27, 60-62`），所以测试通过但实际运行时仍然有问题。

**怀疑 2：代码块修复逻辑的边界情况**

- `hasUnclosedCodeBlock` 只识别 ``` 围栏，不识别 `~~~` 围栏（GitHub 也支持）
- 嵌套代码块（md 里演示 ``` 用法时）会误判开闭次数
- 4 空格缩进代码块未被保护

**怀疑 3：`avoidTableCut` 把整个表格挪到下一段后，当前 chunk 末尾留下悬挂内容**

如果切割点本来在表格中间，`avoidTableCut` 把表格整体挪到下一个 chunk。但当前 chunk 末尾可能留下：
- 标题（`### xxx`）后面没表格 → 标题显得突兀
- 引用块（`> ...`）被截断 → 引用块未闭合

**怀疑 4：微信本身的 md 渲染能力限制**

微信对 md 的支持是不完整的。即使切分完美，长消息在微信里可能：
- 表格显示错乱（列宽不对）
- 代码块没有语法高亮
- 嵌套列表缩进不对

### 我的方案倾向

**方案 A（小改）**：把 `[i/n]` 前缀从行首移走

三种选项：
- A1：前缀放在独立行，用引用块包裹：`> 第 1/3 段\n\n<实际内容>`
- A2：前缀放在 chunk **末尾**：`<实际内容>\n\n---\n[1/3]`
- A3：完全移除前缀（微信消息本来就按时间排序，用户能感知顺序）

**方案 B（中改）**：在切分前先做 md 结构感知

不是按字节切，而是按 md AST 切（标题/段落/列表/代码块作为不可分割单元）。但这需要引入 md 解析库。

**方案 C（大改）**：长消息渲染成图片

最彻底，但改动大、依赖重。

### 抛给 Copilot 的问题

1. **你独立读代码后，认同"怀疑 1（`[i/n]` 前缀）是主因"吗？还是有更隐蔽的问题我漏看了？**
2. 微信单条消息的实际字符/字节限制是多少？4000 是否合理？
3. 方案 A/B/C 你倾向哪个？还是有第四种方案？
4. 微信 md 渲染的实际能力边界在哪（哪些 md 元素能渲染、哪些不能）？

## Round 2 - Copilot

### 验证结论：Pilot 怀疑 1 确为主因，但比你描述的更严重

独立读完了 `splitMessage` 的完整逻辑（line 720-757），我发现一个 Pilot 没提到但更致命的问题：**`[i/n]` 前缀不仅破坏行首 md 结构，还直接废掉了代码块修复逻辑（line 737-749）**。

看执行顺序：

```go
// 第一步：代码块修复（line 737-749）
// 检测到 chunk[i] 有未闭合的 ```，给 chunk[i] 补 ```，给 chunk[i+1] 加 ```lang 重开
chunks[i+1] = "```python\n" + chunks[i+1]  // 修复后：chunk[i+1] 行首是 ```

// 第二步：加前缀（line 752-755），覆盖所有 chunk
chunks[i] = fmt.Sprintf("[%d/%d] %s", i+1, len(chunks), chunks[i])
// 修复后的 chunk[i+1] 变成： [2/3] ```python\n...实际代码...
```

微信解析时，`[2/3] ```python` 不是行首的 ` ``` `，代码块不开始。后面的内容当普通文本渲染，` ``` ` 裸露显示。这就是"有时影响渲染"的直接根因——不是偶尔，而是**只要消息被切分、且包含代码块，就一定渲染错乱**。

### 对怀疑 2 的补充：`~~~` 和 4 空格缩进可以忽略

Claude 输出实务中几乎只用 ` ``` ` 围栏，`~~~` 和 4 空格缩进代码块在 Claude Code 的聊天输出里极少出现。这部分修不修，对用户影响可以忽略。

### 对怀疑 3 的验证：`avoidTableCut` 的实际风险场景

读 `avoidTableCut`（line 838-893）确认了一个 Pilot 没提到的问题：**表格本身 >4000 字节时，该函数完全无力保护**。`avoidTableCut` 的逻辑是把整个表格推到下一段，但当单表格就超过 chunkSize 时，下一段也装不下，最终表格还是会被 `findSafeCutPoint` 的步骤 5（UTF-8 硬切）截断。这时候表格行中间的 `|` 被切断，渲染必然崩。

不过这只是极端情况（单表格超过 ~1333 个中文字），优先级远低于前缀问题。

### 关于方案倾向

**A3（移除前缀）是最小代价、最大收益的选择**。理由：

1. A1（前缀放引用块）和 A2（前缀放末尾）同样引入了新的 md 标记，对渲染仍有干扰
2. 微信消息本身按时间排序到达，用户在聊天窗口里天然看到 1→2→3 的顺序，不需要序号提示
3. 去掉前缀后，代码块修复才能真正生效——修复逻辑本身是对的，问题只出在前缀覆盖了它
4. 变更量极小：删 4 行（line 752-756）或改为仅在 `len(chunks) > 1` 且无 md 内容时加后缀分隔符

**我倾向 A3 + 末尾加一个轻量分隔符**，比如 `\n\n---` 放在 chunk 末尾（不是行首），这样既不影响 md 解析，又能给用户一个"这是多段消息"的视觉提示。

### 问题之外的发现

`findSafeCutPoint` 的 step 5 UTF-8 硬切有一个微妙的正确性问题：`text[pos]` 在边界情况 `pos == 0` 时，`text[0]` 始终是有效 UTF-8 起始字节，所以 `pos` 最终永远不会是 0，不会导致 `splitMessage` 死循环。但这段逻辑的可读性很差，如果后续有人改动，容易引入 bug。不过这是代码质量问题，跟当前议题无关。

## Round 3 - Pilot

### 接受 Copilot 的关键洞察

你指出**执行顺序问题**（先修复代码块再加前缀，前缀让 ` ``` ` 不在行首）——这是比我 R1 更深的洞察。我 R1 只看到"前缀破坏行首 md 标记"，没意识到它还**让代码块修复逻辑的成果失效**。这一点完全成立，我接受。

### 分歧：末尾加 `---` 我反对

你建议 A3 + 末尾加 `\n\n---`。**`---` 在 Markdown 里是水平分隔线（hr）**，会引入新问题：

1. **混淆表格分隔行**：Markdown 表格语法里 `|---|---|` 也是 `---`，如果 chunk 末尾正好是表格，再加一个 `---` 行，微信解析器可能误判
2. **微信渲染 hr 不可控**：微信对 `---` 的渲染（细线、空行、粗线）各版本不一致
3. **视觉噪音**：用户看到一堆横线，干扰阅读
4. **多 chunk 末尾多个 `---`**：3 段消息会显示 3 条横线，过度提示

### 我的方案：完全移除前缀，不加任何替代标记

理由：

1. **微信消息天然按时间排序**——用户看到连续 2-3 条来自同一个 Bot 的消息，自然知道是多段
2. **代码块修复逻辑移除前缀后自动恢复正确**——不需要任何额外配合
3. **最小改动原则**：删 line 752-756 这 5 行就完事
4. **如果未来真要加提示**，可以放一个**纯文本（非 md 语法）的尾巴**，比如 `\n\n（1/3）`——这种圆括号包裹的中文不会被任何 md 解析器识别为结构，纯视觉提示

## 最终共识

### 根因

`splitMessage` 在 `wechat.go:752-756` 给每个 chunk 加 `[i/n] ` 前缀，导致：

1. **前缀破坏行首 Markdown 结构**：chunk 以 `#`、`-`、`|`、`>` 等 md 标记开头时，前缀让这些标记失效
2. **前缀废掉代码块修复逻辑成果**：执行顺序是先修复代码块（line 737-749）再加前缀（line 752-756）。修复后的 chunk（如 ` ```python\ncode\n``` `）被加上前缀后变成 `[2/3] ```python\n...`，` ``` ` 不再在行首，微信不识别为代码块开头

只要消息被切分、且包含代码块或 md 行首标记，就一定渲染错乱。这不是偶发问题。

### 修复方案

**纯减法修复**：删除 `wechat.go:752-756` 的 `[i/n]` 前缀逻辑。

```go
// 删除这 5 行：
if len(chunks) > 1 {
    for i := range chunks {
        chunks[i] = fmt.Sprintf("[%d/%d] %s", i+1, len(chunks), chunks[i])
    }
}
```

删除后：
- 现有代码块修复逻辑（line 737-749）直接生效
- `avoidTableCut` 和 `findSafeCutPoint` 不受影响
- 多段消息天然按时间排序到达，用户能感知顺序

### 不做的事

- **不加任何替代标记**（不加 `---`、不加 `（1/3）` 纯文本尾巴）—— 等未来用户反馈再加
- **不动 chunkSize=4000** —— 微信单条消息实际限制未知，留作独立议题
- **不修 `~~~` / 4 空格缩进代码块** —— Claude 输出实务中极少出现
- **不修超大表格（>4000 字节）无法保护** —— 极端情况，优先级低

### 改动量

1 个文件，删 5 行代码。
